# 最適解探索 — 契約

## 何を確かめるのか

設計文書の中心の主張は「**目的は単一、最適解は複数**」であり、それを4つの装置で守っている（連鎖群／頻度依存／情報遮断／外生ショック）。

**この探索そのものが、その主張の最終試験になる。**

- 総当たりに近い探索で**支配戦略が1本見つかったら、設計の負け**
- 見つからず、勝ち筋が複数に割れ、しかも相手によって最適が変わるなら、**装置が実際に効いている証拠**

「検査を通すために係数をいじる」のは禁止。**否定的な結果が出たらそのまま報告すること。** それがこの探索の目的。

## 評価器の契約（Node側）

`node tools/eval.js` が stdin から JSON を読み、stdout に JSON を返す。

**入力**
```json
{
  "policies": [ { "id": "p001", "cards": {...}, "captiveAxis": "武力", "border": "accept",
                  "promote": "martial", "warAppetite": 0.6 } ],
  "seeds": [1,2,3, ...],
  "gens": 200,
  "opponents": ["martial","agrarian", ...]
}
```

**出力**（policy × seed の1行ずつ）
```json
{ "results": [ { "id":"p001", "seed":1, "opponent":"martial",
                 "power":1234, "pop":180, "gens":200, "extinct":false,
                 "wins":7, "losses":3, "admixture":0.31, "morale":0.62,
                 "regimeGrudge":12.4, "yieldRate":41.2 } ] }
```

**絶対規則**
- 本物の `src/sim/` を叩くこと。**Python側でゲームを再実装しない。** 別のゲームを最適化することになる
- `Math.random()` 禁止。種から決定的に
- 1回の呼び出しで数百〜数千件を捌けること（起動コストを毎回払わない）

## 探索の作法（Python側）

**過適合を避けること。** この企画では既に「3種で測ったら綱引きに見えたが、30種で測ったら単なる種不足だった」という失敗をしている。

- 1つの方針は**最低30種**で評価し、平均と信頼区間で比べる
- 探索に使った種と、最終判定に使う種を**分ける**（ホールドアウト）
- 「たまたま良かった1本」を最適解と呼ばない

## 答えるべき4つの問い

1. **支配戦略はあるか** — 全種・全相手で勝つ方針が1本あるか。あれば設計の敗北なので、どのカードが効いているかまで特定する
2. **勝ち筋は何本あるか** — 上位方針をクラスタリングして型の数を数える。1本なら失敗、複数なら成功
3. **最適は相手で変わるか** — 相手の思想ごとに最良方針が違うか（設計の主張：「統治の正解は自国民依存でコピーできない」）
4. **上手い下手の差は観測できるか** — 最良／中央／ランダムでどれだけ差がつくか。差が小さければ、レビューで指摘された「上達を測る定規がない」が実測で裏付けられたことになる

## 出力

`tools/report-search.md` に、4つの問いへの答えを数字で。ASCIIの図でよい。
